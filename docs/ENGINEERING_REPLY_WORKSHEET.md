# 學習單產生器：工程回覆（規格 §12 第 2–6 項）與匯出技術選擇

- 日期：2026-11-15　對應：《學習單產生器：教師選項與 SOP 整合規格》（2026-11-14）
- 實作：分支 `feature/worksheet-generator`（改版第 3 步）。API 契約見 `docs/API.md`「Phase 2.3」；模型實測依據見 `docs/LLM_VALIDATION.md`。
- 這一版**不含**：外部資源搜尋（§4.3）、AI 資深教師（§4.5）、歷屆考題分析（沒有資料）。教材並排與註記來自教材庫（Phase 2.2），本分支只把它接進產生器。§9.6 只做了決定性的「詞彙級別檢查」。

## 0. 這一版做到的流程

直接貼教材（或從課例按「產生學習單」）→ 四個選項區塊（全部可不選）→ 背景產生（四步，各一次模型呼叫＋最多一次修復）→ 程式組裝學生版與教師參考版、各選定版本 → 平台內編修（改字、改答案、拖曳／上下移、單一區塊重新產生與復原、關掉暖身或 Exit ticket）→ 詞彙級別檢查 → 匯出 DOCX／PDF。課例內容只有教師在「同步回課例」對話框確認後才會改。

截圖：`docs/design/overhaul/implemented/worksheet/`。

## 1. 第 2 項：介面

| 功能 | 介面 | 說明 |
|---|---|---|
| 預覽 | 結果頁右側是印刷樣式的學習單（`article.ws`，襯線字），左側是教材欄（可收起） | 預覽與匯出用同一份投影（`worksheet::assemble::project`），看到的就是印出的 |
| 學生版／教師參考版 | 「顯示版本」切換：學生版｜教師參考版 | 參考答案、依據、教師備註只在教師參考版畫出（學生版的 DOM 與 API 回應裡都沒有這些欄位） |
| 版本分頁 | 分頁只列教師選的版本（基礎版／一般版／進階版） | 每題、每個鷹架可勾選出現在哪些版本 |
| 拖曳 | 每個區塊有拖曳把手；同時有「上移」「下移」按鈕（鍵盤可用） | 改順序即自動儲存成新版本 |
| 局部重新產生 | 每個區塊的「重新產生」（金色） | 只重跑該區塊需要的步驟；其他區塊不動；請求一定與前一次不同（閘道快取） |
| 版本復原 | 「復原上一版」只在有上一版時出現；可一路復原到最早 | 取代前的區塊存在 `worksheet_block_history`；整份學習單另有只增不改的版本紀錄（`worksheet_versions`，含 `cause`） |
| 失敗 | 每一步各自顯示「完成／略過／沒有成功＋原因」；沒產生成功的區塊留空並說明 | 任何失敗都不擋手動編輯 |

教材欄是可替換的插槽（`web/src/components/worksheet/MaterialPane.tsx`、`WorksheetPage` 的 `materialPane`）；後端只認 `WorksheetMaterial { title, paragraphs[{id,text}], source }`（`api/src/worksheet/material.rs`）。已接上教材庫（Phase 2.2）：貼上的文字存進教材庫並連到學習單，教材欄顯示 `MaterialViewer`（可選字加註記），勾了「提供給 AI」的註記會帶進產生的 prompt；產生流程、檢查、組裝與匯出都沒有因此改動。上傳檔案（PDF、DOCX 等）作為學習單教材的入口還沒做：目前要先放進課例或貼上文字。

## 2. 第 3 項：DOCX 與 PDF 的產製方式、版面與字型

**原則**：後端產生、直接串流回瀏覽器、不存檔（這一版沒有物件儲存）。兩種格式都來自同一份投影，所以內容、題號、版本差異與「答案只在教師版」在三處（預覽、DOCX、PDF）一致。

| | 選擇 | 理由 | 放棄的做法 |
|---|---|---|---|
| DOCX | 直接寫 WordprocessingML，用 `zip` crate 打包（`api/src/worksheet/export.rs`） | 輸出全是 Word 原生物件（段落、表格、段落框線當作答線），教師可以直接改；不需外部程式；依賴只有 `zip`（純 Rust，deflate） | `docx-rs` 等函式庫：多一層抽象但沒有省多少；LibreOffice 轉檔：映像檔大 300MB 以上、啟動慢 |
| PDF | `krilla` 0.8（純 Rust PDF 產生器，字型子集化內建）＋自寫的簡單排版（斷行、分頁、作答線、表格框、頁碼） | 不需 Chromium／wkhtmltopdf／LibreOffice；在 2 核心主機上編譯可接受（約 300 個 crate 中新增約 40 個）；執行時只是 CPU 計算，一頁不到幾十毫秒 | 無頭瀏覽器（Chromium 約 400MB，記憶體吃重）；Typst（排版最好，但編譯與相依多出一個數量級） |
| 英文字型 | Libertinus Serif（Regular／Bold／Italic，SIL OFL 1.1）編進執行檔（`api/assets/fonts/`，授權在 `OFL.txt`） | 與平台的印刷樣式一致；只嵌入用到的字（子集化），一份 PDF 約 30–60KB | |
| 中文字型 | PDF：執行時讀 `WORKSHEET_CJK_FONT`，映像檔安裝 `fonts-wqy-microhei`（約 5MB）並設好路徑；DOCX：指定字型名（英文 Times New Roman、中文新細明體），不嵌入 | 學生版應為全英文，中文只出現在教師備註；沒有中文字型時，含中文的 PDF 回 409 並請教師改用 DOCX，不會印出方框 | 把 Noto CJK 編進執行檔（16MB 以上）；不必要 |

映像檔：`docker build .` 通過，結果約 213MB（runtime 只多了中文字型）。

版面：A4、邊界 2cm；標題、班級／座號／姓名列、「Today I can …」、各區塊（A. Warm-up、B. Paragraph 1: Find …、Exit ticket）、分步指示（灰字）、字詞表、語言／教學鷹架、題目（選擇題選項 (A)–(D)、表格整理給 2×3 格、圖像組織給一個框、其他給作答線；行數基礎版 2、一般版 3、進階版 4，段落寫作再多 2）。教師參考版在每題下方以深金色印「Answer」「Evidence」，並印教師備註與字彙級別。檔名：`<檔名>_<版本>_<學生版|教師參考版>.docx|pdf`（RFC 5987）。

## 3. 第 4 項：後端欄位、API、模型、儲存、權限與估時

**資料表**（`api/migrations/0010_worksheets.sql`）

| 表 | 用途 | 重點欄位 |
|---|---|---|
| `worksheets` | 一份學習單（屬於一位教師） | `lesson_id`（可為 null＝獨立）、`class_id`、`title`、`filename`、`material`（教材快照，接縫形狀）、`settings`（四區塊＋版本＋預計完成時間，規格標籤原字）、`suggested`（系統建議，畫面上打星號）、`brief`（從課例帶入、可刪改的任務／暖身／字彙／Exit ticket 想法）、`source_sop_version_id`、`generated`、軟刪除 |
| `worksheet_versions` | 只增不改的內容版本 | `version_no`（系統管理）、`content`（目標、依序的區塊；每個區塊有學生看的內容、教師參考答案與備註、鷹架、`origin` = teacher｜ai｜ai_edited）、`cause` |
| `worksheet_block_history` | 單一區塊重新產生前的狀態（復原用） | `block_id`、`block`、取代它的 `interaction_id` |
| `worksheet_jobs` | 背景工作（一步一列） | `run_no`、`step`、`block_id`、`status`、`outcome`、`phase`、`message`、`interaction_id`、`context` |
| `worksheet_checks` | 詞彙級別檢查結果 | 綁 `worksheet_version_id`（之後有新版本即標為過期）、`level`、`target_level`、`result` |

另新增 4 個 prompt key（`worksheet_tasks`、`worksheet_warmup`、`worksheet_scaffolds`、`worksheet_exit_ticket`，可在後台改版）與 4 個鷹架代碼（`SC-WS-TASKS`、`SC-WS-WARMUP`、`SC-WS-SCAFFOLDS`、`SC-WS-EXIT`）。每次模型呼叫寫一列 `ai_interactions`（教材只留字數與雜湊）；復原重新產生的區塊會記一筆 `teacher_decisions`（reject）。

**API**：見 `docs/API.md`「Phase 2.3」，共 19 個端點（清單、建立〔直接／從課例〕、讀、存、換教材、刪、產生、輪詢、區塊重新產生、復原、投影、版本、同步預覽、同步套用、連結、另存為課例、詞彙檢查、檢查結果、匯出）。

**模型流程**（依 `docs/LLM_VALIDATION.md` §10）：一步一次呼叫、每次都設 `max_tokens`（依份量：任務 3000–6000、暖身 2000、鷹架 2000–5000、Exit ticket 1200）、修復呼叫一定改變請求（temperature +0.4 並附未通過的檢查）、標籤只能來自 enum、字彙級別只查資料、**學習單由程式組裝**（不呼叫 (g)）。檢查移植自 `research/sop-validation/chain/checks.py`；第二次仍不合格的部分由程式拿掉並記錄，整步沒有可用內容才留空並說明。

**權限**：所有端點只能存取自己的學習單、自己的課例與班級（其他回 404）。

**估時**（一位工程師；本分支實際約 3 天的工作量）

| 項目 | 估時 |
|---|---|
| 資料模型、API、標籤驗證 | 1.5 天 |
| 四步產生流程、檢查與修復、程式組裝、假模型 | 3 天 |
| 結果編修介面（版本、學生／教師、拖曳、重新產生、復原、自動儲存） | 3 天 |
| 匯出（DOCX、PDF、字型） | 2 天 |
| 同步回課例、連結與另存課例、詞彙級別檢查 | 1.5 天 |
| 測試（後端整合 11 項、前端 15 項）與文件 | 2 天 |
| **以國網中心模型做真實資料回歸與調 prompt（尚未做）** | 3–5 天 |

## 4. 第 5 項：如何從學習單萃取並驗證結構化設計規則

做法與第一版結果在 `docs/LLM_VALIDATION.md` §4、§12（第 5 項），這裡補上與本實作的關係：

1. **萃取**：270 份（實收）學習單 → 文字 → 模型依固定 schema 逐份標註（活動順序、資訊處理功能、學生任務、作答方式、三種鷹架、暖身／收尾／目標／答案／分級，標籤全用規格原字）→ 統計 → 16 條規則（DR-01–DR-16），每條附證據數字與對應的自動檢查（`research/sop-validation/rules/design_rules.json`）。
2. **驗證**：(a) 標註正確率：AI 代理抽查 16 份為初估，正式驗證需 2 位教師各判讀 50 份、算一致性（關鍵欄位目標 ≥ 85%）；(b) 與關鍵字規則交叉比對，差異大的欄位不當精確比例；(c) 規則由教師逐條確認；(d) 成效以「有／無規則」對同一批文章比較自動檢查通過率並做教師盲評。
3. **本實作採用的方式**：規則中**能寫成程式的**直接進程式，不靠 prompt：讀前（暖身）固定在主要任務之前（DR-01、DR-10）、依段落順序（DR-04）、至少 3 種功能且最後是分析／比較／創造（DR-02、DR-03，檢查）、每個區塊都有分步指示（DR-09，系統自動加入）、Exit ticket 題數少（DR-14，2–3 題）、分級與參考答案（DR-15，程式組裝）、全英文（DR-16，檢查）。**依 §6.3 的結果，「讀前→讀中→讀後」這類會與暖身步驟衝突的規則沒有放進 prompt**；其餘規則等教師確認後再改寫放入 `worksheet_tasks` 的新 prompt 版本（後台可改版、舊版保留、每次呼叫記錄版本，可直接做前後比較）。

## 5. 第 6 項：少量代表性範例的選取、去識別與成效驗證

- **選取標準**（`research/sop-validation/worksheets/select_fewshot.py`，全由清冊計算）：閱讀型、英文指示、未被截斷、4–9 個區塊、有暖身、最後一個區塊是分析／比較／創造；以功能種類＋作答方式種類＋鷹架類型數＋收尾反思＋學習目標評分；同版本同冊最多 2 份、同課最多 1 份、同設計者最多 2 份。候選：W048、W086、W096、W238、W078、W079、W089、W093。
- **去識別**：範例只用「活動骨架」（區塊的類型、功能、學生任務、作答方式、鷹架）與一句設計手法說明，不含學習單原文、標題、教師或校名；這同時避開著作權與個資。若改用含原文的範例，前提是教師同意、移除姓名／校名／班級／網址，且不含教科書課文。
- **成效**：§6.3 的對照顯示骨架範例＋規則沒有提高自動檢查通過率（第一次通過率反而較低，prompt 變長後失控較多），但題目寫法較像教師慣例。**因此這一版的 prompt 不放範例**；要加入時在後台為 `worksheet_tasks` 新增一個 prompt 版本即可（舊版保留，每次呼叫記錄所用版本），是否採用以教師盲評決定：同一批 20 篇文章、有／無範例各產生一次，2–3 位教師盲評「題目可直接用的比例」「像不像教師會出的題」，並看自動檢查通過率不得下降。

## 6. 尚待確認與已知限制

1. **還沒有用國網中心模型實跑這條產生流程**（本分支只用假模型與既有的研究實測結果）。上線前要用 `research/sop-validation/passages` 等文章跑一輪，確認四步的通過率與耗時（研究實測 (c) 43 秒、(d) 40 秒、(e) 52 秒、(f) 13 秒的中位數，整份約 2.5 分鐘；不需等 (g)）。
2. 單一區塊重新產生時，暖身與 Exit ticket 會參考目前的主要任務概要；但活動區塊重新產生時沒有重新產生暖身的字彙（字彙仍可手改）。
3. 同步回課例目前對應「目標」與「逐段任務」；學習單的暖身與 Exit ticket 尚未寫回 SOP 的第 6、7 步。「建議補充至 CoRe」只留了介面與程式掛勾（`sync::core_suggestions`，永遠回空陣列）。
4. DOCX 字型只指定名稱（Times New Roman／新細明體），在沒有這些字型的電腦上由 Word 替代。
5. 詞彙級別檢查分析的是學生版的印出文字；片語、詞義與詞性的限制同 Phase 2.0（結果頁會列出）。
